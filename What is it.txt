# EDGEQUERY

### Embedded Data Analytics & Edge Computing on ESP32

**Analyze locally. Store persistently. Process efficiently.**

EDGEQUERY is an experimental embedded data analytics platform that transforms an ESP32 DevKit V1 into a standalone, Wi-Fi-enabled CSV analysis engine with a proposed external-storage subsystem.

The project combines embedded data processing, browser-based visualization, persistent dataset storage, and resource monitoring to explore data analytics on resource-constrained hardware.

The laptop or smartphone acts as the user interface, while the ESP32 performs the core parsing and profiling operations.

The proposed external-storage extension introduces persistent dataset archives, analysis reports, and storage-management capabilities without requiring the complete dataset to reside in RAM.

---

## Overview

EDGEQUERY creates its own Wi-Fi access point and hosts a browser-based dashboard directly on the ESP32.

Users connect to the device, upload CSV datasets, inspect their structure, analyze missing values, calculate numeric statistics, and examine the results through an interactive interface.

The external-storage architecture introduces an SPI-connected storage device for retaining uploaded datasets and generated reports.

By separating persistent storage from working memory, EDGEQUERY aims to support larger datasets while maintaining a memory-conscious processing pipeline.

**Project status:** External-storage architecture proposed; firmware integration and hardware validation pending.

### Key Features

* **Standalone Wi-Fi access point:** Connect directly to EDGEQUERY without requiring an existing Wi-Fi network.
* **Streaming CSV parser:** Processes incoming CSV data incrementally.
* **Dataset profiling:** Reports row counts, column counts, missing values, and detected column types.
* **Numeric statistics:** Calculates minimum, maximum, and average values for supported numeric columns.
* **Distinct-value tracking:** Tracks a bounded number of distinct-value hashes.
* **Dataset preview:** Displays a limited sample of uploaded records.
* **Interactive web dashboard:** Provides browser-based dataset visualization and management.
* **Live device telemetry:** Displays heap usage, CPU activity estimates, and processing information.
* **Persistent dataset storage:** Proposed support for saving uploaded datasets to external storage.
* **Analysis report storage:** Proposed support for saving schema profiles and statistical summaries.
* **Dataset management:** Planned browsing, selection, and deletion of stored datasets.
* **Storage monitoring:** Planned reporting of total, used, and available storage.
* **Analysis history:** Planned retention of previous analysis reports.
* **Light and dark themes:** Provides alternative dashboard appearances.
* **Local processing:** Core CSV parsing and profiling do not require cloud processing.

## Software Architecture

EDGEQUERY is organized around the following logical components.

### 1. Wi-Fi and HTTP Server

The ESP32 operates as a Wi-Fi access point and hosts an HTTP server on port 80.

The browser communicates with the firmware through HTTP endpoints for dataset uploads, telemetry, and supported queries.

### 2. Streaming CSV Processing Engine

The parser processes incoming CSV data incrementally rather than loading the complete file into RAM.

Supported parsing features in the existing design include:

* Comma-separated fields
* Quoted fields
* Commas inside quoted fields
* Escaped double quotes
* LF and CRLF line endings
* Newlines inside quoted fields
* UTF-8 byte-order mark removal from the first header field
* Bounded field buffering

### 3. Dataset Profiling Engine

The analyzer maintains metadata and statistics for each column, including:

* Column name
* Detected data type
* Missing-value count
* Non-empty-value count
* Approximate distinct-value tracking
* Numeric minimum and maximum
* Numeric sum
* Limited dataset preview

Supported detected types include integer, float, boolean, date, text, and unknown.

Type detection uses lightweight heuristics rather than a complete data-type inference engine.

### 4. Storage Manager — Proposed

The storage manager will provide a dedicated interface between the analysis engine and the external filesystem.

Planned responsibilities include:

* Storage initialization
* Filesystem availability checks
* File creation and writing
* Incremental dataset storage
* File reading
* Dataset deletion
* Free-space reporting
* Handling failed writes and unavailable storage

### 5. Dataset Manager — Proposed

The dataset manager will coordinate dataset uploads, persistent storage, analysis requests, and file metadata.

It will allow the application to distinguish between a newly uploaded dataset, a stored dataset, and a completed analysis.

### 6. Report Manager — Proposed

The report manager will serialize analysis results into persistent JSON reports.

Reports may include dataset dimensions, column metadata, missing-value counts, numeric statistics, processing duration, and a reference to the source dataset.

### 7. Browser Dashboard

The existing interface provides dataset upload, progress indicators, schema visualization, preview tables, numeric statistics, telemetry, and theme selection.

The proposed storage extension will add a dataset browser, storage-capacity indicators, file-management controls, and analysis-history navigation.

## External Storage Architecture

The proposed storage subsystem uses an SPI-compatible microSD module and a FAT-compatible filesystem supported by the ESP32 Arduino environment.

A possible directory structure is:

```text
/EDGEQUERY/
    /datasets/
        dataset_001.csv
        dataset_002.csv
        dataset_003.csv

    /reports/
        dataset_001.json
        dataset_002.json

    /config/
        settings.json

    /history/
        analysis_log.csv
```

### Directory Responsibilities

| Directory   | Purpose                               |
| ----------- | ------------------------------------- |
| `/datasets` | Stores uploaded datasets              |
| `/reports`  | Stores generated analysis reports     |
| `/config`   | Stores application settings           |
| `/history`  | Records completed analysis operations |

The firmware should create missing directories during initialization and handle unavailable storage, full storage, failed writes, and interrupted uploads gracefully.

These directories and storage operations are part of the proposed implementation and are not yet confirmed as operational.

## SPI Wiring

For a typical ESP32 DevKit V1 using its default VSPI pins, the proposed wiring is:

| ESP32 Pin | microSD Module Pin              |
| --------- | ------------------------------- |
| GPIO 18   | SCK / CLK                       |
| GPIO 23   | MOSI / DI                       |
| GPIO 19   | MISO / DO                       |
| GPIO 5    | CS                              |
| 3.3 V     | VCC, if supported by the module |
| GND       | GND                             |

The selected pins must match the firmware configuration.

Use a module compatible with the ESP32's 3.3 V logic, and verify the module's power requirements before connecting it.

## Dataset Processing Pipeline

The proposed external-storage workflow is designed to minimize RAM consumption.

1. **Receive:** The browser uploads a CSV dataset through the HTTP server.
2. **Validate:** The firmware validates the filename, upload state, file size, and available storage.
3. **Store:** Incoming chunks are written incrementally to external storage.
4. **Analyze:** The CSV parser processes the dataset incrementally.
5. **Profile:** The analyzer calculates supported statistics and maintains schema metadata.
6. **Generate:** The report manager creates a structured JSON analysis report.
7. **Persist:** The report is saved externally, and the analysis history is updated.
8. **Display:** The dashboard presents the analysis results and storage information.

The implementation should use temporary filenames during uploads and promote files to their final names only after successful completion.

This reduces the risk of treating an incomplete upload as a valid dataset.

**Important:** External storage increases persistent capacity, not RAM capacity or processing speed. Supported dataset sizes will depend on the final implementation, parser constraints, filesystem behavior, and available working memory.

## Resource Limits

The existing firmware uses the following limits.

| Resource                         | Current Configuration |
| -------------------------------- | --------------------: |
| Maximum dataset size             |                 3 MiB |
| Maximum columns                  |                    64 |
| Maximum column-name buffer       |              32 bytes |
| Maximum field buffer             |             128 bytes |
| Maximum preview rows             |                     8 |
| Maximum preview field buffer     |              32 bytes |
| Distinct-value hashes per column |                    32 |
| HTTP server port                 |                    80 |

The proposed external-storage edition aims to replace the fixed upload restriction with a configurable limit validated against available storage and processing constraints.

The initial implementation should retain the existing column, field, preview, and distinct-value limits until testing demonstrates that increasing them is safe.

The maximum supported file size must be established through testing rather than assumed to equal the storage device's total capacity.

## API Endpoints

The existing firmware registers the following endpoints.

| Method | Endpoint       | Purpose                                           |
| ------ | -------------- | ------------------------------------------------- |
| GET    | `/`            | Serves the embedded dashboard                     |
| GET    | `/status`      | Returns device and dataset telemetry              |
| POST   | `/analyze`     | Receives and processes an uploaded dataset        |
| POST   | `/query`       | Handles supported dataset questions               |
| POST   | `/sql-explain` | Explains a limited set of recognized SQL patterns |

The external-storage implementation may introduce additional endpoints for dataset listing, deletion, storage information, and stored-report retrieval.

Those endpoints should be documented after their routes and behavior are implemented.

The existing query interface is rule-based. It does not provide arbitrary SQL execution, general-purpose natural-language understanding, or machine-learning inference.

## Installation and Setup

### Requirements

* ESP32 DevKit V1
* USB data cable
* Arduino IDE
* Compatible ESP32 Arduino board package
* SPI-compatible microSD reader module
* Compatible microSD card
* Laptop or smartphone with Wi-Fi and a browser

### Step 1: Clone the Repository

```bash
git clone https://github.com/YOUR_USERNAME/EDGEQUERY.git
cd EDGEQUERY
```

Replace `YOUR_USERNAME` with your GitHub username.

### Step 2: Prepare the Firmware

Open the EDGEQUERY Arduino sketch.

Configure the storage pins and storage settings in the firmware when the storage integration is available.

### Step 3: Connect the Storage Module

Connect the SPI microSD module according to the wiring table.

Check power requirements and wiring before powering the device.

### Step 4: Select the Board

In Arduino IDE, select:

`Tools → Board → esp32 → DOIT ESP32 DEVKIT V1`

Select the appropriate serial port.

### Step 5: Compile and Upload

Compile the firmware and upload it to the ESP32.

Open Serial Monitor at 115200 baud to inspect startup messages, the access-point address, and storage initialization status.

### Step 6: Connect to EDGEQUERY

Connect your laptop or smartphone to the Wi-Fi network advertised by the ESP32.

Open the IP address printed in Serial Monitor. The default ESP32 soft-AP address is commonly `192.168.4.1`, but the address printed by the firmware is authoritative.

### Step 7: Analyze a Dataset

Once external-storage integration is implemented:

1. Open the dashboard.
2. Select a CSV file.
3. Upload the dataset.
4. Wait for storage and analysis to complete.
5. Inspect the schema, preview, missing-value profile, and numeric statistics.
6. Verify that the dataset and report appear in the storage manager.

The final workflow and supported upload limit must be confirmed through hardware testing.

## Reliability and Data Integrity

Persistent storage introduces additional failure modes that must be handled explicitly.

The implementation should include:

* File-size and free-space validation
* Incremental file writes
* Write-error detection
* Incomplete-upload cleanup
* Safe filename handling
* Filesystem initialization checks
* Graceful handling of missing storage
* Recovery from interrupted operations where practical
* Validation before deleting stored files
* Protection against invalid filesystem paths

The application should not mark a dataset as successfully stored until the write operation has completed successfully.

Analysis reports should be generated only after the corresponding dataset has been processed successfully.

---

## Privacy and Data Handling

EDGEQUERY is designed for local data processing without requiring a cloud analytics service.

The proposed external-storage extension will retain datasets and reports on the connected storage device.

Local processing does not automatically guarantee security. Access-point credentials, request validation, filesystem path validation, and dataset-management permissions must be considered before sensitive datasets are used.

The storage subsystem should not expose arbitrary filesystem access through the web interface.

## Current Limitations

EDGEQUERY remains an experimental embedded analytics project.

Known limitations of the existing implementation include:

* CSV input only; XLSX, JSON, and Parquet are not implemented.
* Column types are inferred using lightweight heuristics.
* Numeric statistics use floating-point accumulation.
* Distinct-value tracking is bounded and hash-based.
* The dataset preview stores only a limited number of rows.
* Natural-language-style questions are handled by predefined rules.
* SQL input is recognized selectively rather than executed by a general-purpose SQL engine.
* CPU telemetry is an estimate rather than comprehensive hardware performance monitoring.
* Malformed-input and memory-pressure scenarios require further testing.
* Multi-client behavior and maximum reliable throughput require validation.

Additional limitations apply to the proposed storage extension:

* SPI storage initialization has not yet been integrated.
* Persistent dataset uploads have not yet been implemented.
* Storage telemetry has not yet been implemented.
* Persistent analysis reports and history are planned.
* Maximum reliable dataset size has not yet been established.
* Power-loss recovery and storage-failure handling require testing.
